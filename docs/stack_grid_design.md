# Мультиблюпринт по глубине стека: как подключить, не ломая стол

Объяснялка, 28.09.2026, по просьбе пользователя («как красиво и элегантно, не поломав ничего, подключить
мультиблюпринт, чтоб он был максимально универсален под любого ИИ»). Это предложение архитектуры; реализует
основная сессия после утверждения. Числа для порогов — из матрицы шага 2 (`docs/stack_depth.md` §5).

## 1. Как сейчас сажают за стол

Стол ничего не знает о блюпринтах. Движок (`negpluribus/engine.py`) зовёт у каждого места три метода
базового класса `Agent` (`negpluribus/agents/base.py`):

```
reset(seed)                 # перед раздачей
act(obs) -> Action          # решение по наблюдению (карты, борд, стеки, ставки, история)
end_hand(record, my_seat)   # после раздачи
```

За стол можно посадить кого угодно с этими тремя методами: случайного, коллера, друга (`seats/mozg.py`),
блюпринт, поиск. Сейчас два «умных» агента:

- `BlueprintAgent(strategy, bucketer, grid)` (`agents/blueprint.py`): ключ инфосета → стратегия → действие.
  Ключ без стека, поэтому агент технически играет на любой глубине (off-map 0–0.4 % по замеру), но
  стратегией той глубины, на которой учился.
- `CoreSearchAgent(resources, config)` (`agents/core_search.py`): `SearchResources` = игра + блюпринт +
  бакетер + таблицы; на каждом решении строит подыгру от **реальных** стеков (`obs.starting_stacks`),
  блюпринт нужен для диапазонов, листьев и префлопа.

Конфиг веб-столика (`webapp/bots.json`): на бота — `stack_bb`, сетка, путь к блюпринту, бакетер, кеш.

## 2. Предложение: обёртка `StackGridAgent`

Один новый класс-агент, без правок движка, стола, блюпринта и поиска.

```
StackGridAgent(points, inner_factory, rule)
  points        : [(stack_bb, blueprint, bucketer), ...]   — точки сетки, из манифеста
  inner_factory : (point) -> Agent                          — что сажать в точке: BlueprintAgent,
                                                             CoreSearchAgent, RNR/эксплойт-агент — любой
  rule          : пороги переключения (см. §3)
  reset(seed)   : сбрасывает всех внутренних (или ленивая инициализация)
  act(obs)      : на ПЕРВОМ решении раздачи считает эффективный стек героя и выбирает внутреннего агента;
                  до конца раздачи все act/end_hand идут ему
  end_hand(...) : тому же внутреннему агенту
```

- **Эффективный стек героя** = min(свой стек, max(стеков живых оппонентов)) в начале раздачи, из
  `obs.starting_stacks` (или `stacks + street_bets` на первом решении). В HU это min(свой, чужой), в 3-max —
  та же формула (приближение, `docs/stack_depth.md` §6).
- **Универсальность:** обёртка не знает, что внутри. Тот же класс собирает «сетку блюпринтов», «сетку
  поисков» (у каждого своя `SearchResources` с блюпринтом точки; подыгра и так строится от реальных стеков),
  «сетку эксплойт-агентов». Внутренние агенты делят бакетер и таблицу корзин (один бакетер на всю сетку).
- **Память:** pot16 — 30…234 МБ на точку, 7 точек ≈ 0.7 ГБ; pot64 ≈ ×4. Таблица корзин одна.
- **Что не меняется:** ключи, движок, стол, eval_archetypes, AIVAT (известный игрок = внутренний агент
  раздачи; в лог руки писать, какая точка выбрана).

## 3. Пороги: конфиг, а не код

Манифест сетки — JSON в `data/`, например `data/stack_grid_pot16_s0.json`:

```json
{
  "bucketer": "data/buckets_hunl200w3_pot16_s0.json",
  "grid": {"preflop": [0.5, 1.0, 3.0], "postflop": [0.5, 1.0, 2.0, 4.0], "max_raises": 3},
  "points": [
    {"stack_bb": 20,  "blueprint": "data/blueprint_hunl20w3_pot16_s0.bin",  "trained": "GPU b16384 600M, 28.09"},
    {"stack_bb": 50,  "blueprint": "data/blueprint_hunl50w3_pot16_s0.bin",  "trained": "GPU b16384 600M, 28.09"},
    {"stack_bb": 200, "blueprint": "data/blueprint_hunl200w3_pot16_s0.bin", "trained": "CPU 400M, 27.09"}
  ],
  "rule": {"kind": "boundaries", "upper": [28, 53, 84, 122, 173]}
}
```

- `rule.kind = "boundaries"`: явные верхние границы каждой точки (из матрицы шага 2). Пока матрицы нет —
  `"nearest_log"`: ближайшая точка по отношению, при равенстве глубже (по первым замерам мелкий блюпринт на
  глубоком столе теряет больше, чем глубокий на мелком — проверяется перезапуском матрицы).
- Границы — числа в файле, не в коде: перемерили матрицу — поправили JSON.
- Бот в `webapp/bots.json` / у `eval_archetypes` получает вместо `blueprint` поле `stack_grid` с путём к
  манифесту; остальное как раньше.

## 4. Проверки приёмки (правило «каждый шаг бьёт предыдущий»)

1. **Юнит:** при равных стеках = точке сетки обёртка бит в бит повторяет одиночный агент этой точки.
2. **Дуэль с переносом стеков** (как `carry` в веб-столике, без сброса): `StackGridAgent` над блюпринтами
   против одиночного 200bb; и над поисками против одиночного поиска. Принимаем, только если обыгрывает.
3. **Дуэль на фиксированных чужих глубинах** (50, 84, 122): сетка против одиночного 200bb — должна дать
   те же +18 / … , что родные точки в матрице.
4. В логах рук — выбранная точка и эффективный стек, чтобы AIVAT и разбор видели переключения.

## 5. Что остаётся открытым

- 3-max с тремя разными стеками: формула эффективного стека — приближение; точный путь — сеть (В).
- Смена глубины **внутри** раздачи невозможна и не нужна: стеки меняются только между раздачами.
- Поиск внутри точки уже строит дерево от реальных стеков; вопрос только, чей блюпринт даёт диапазоны.


## 6. Рецензия основной сессии (28.09, 22:30; по коду master f4fc212)

Общее: обёртка над `Agent` с выбором внутреннего агента на первом решении раздачи — правильный минимальный
шаг; он ничего не меняет в blueprint'ах и поиске и проверяется бит в бит на точках сетки. Замечания по пунктам.

1. **Ресурсы поиска на точку.** `SearchResources.build` сейчас на каждый вызов создаёт свой C++-бакетер с кэшем
   (`core_bucketer(bucketer, cache_caps)` + `load_cache` — 577 МБ приватной памяти на pot16) и свой
   `search_bucketer` с таблицами; `SearchGame(spec, cbk, lookup, search_bucketer)` принимает уже готовые объекты.
   Значит, делить можно и нужно: один C++-бакетер с кэшем и один бакетер подыгры с таблицами на всю сетку,
   `build(..., core_bucketer=…, search_core_bucketer=…)` — небольшая правка. Неделимое на точку: только lookup
   blueprint'а (pot16 ≈ 105 МБ) и `SearchGame` (таблицы по борду строятся на поиск и живут недолго). Оценка: 8 точек
   ≈ 0.85 ГБ lookup'ов + 0.6 ГБ общего кэша + рабочие таблицы поиска (≤ 1.5 ГБ по правилу) — влезает в 32 ГБ без
   подкачки, но грузить точки лениво (по первому обращению), с верхней границей числа одновременно загруженных
   (LRU на 3–4 точки), иначе рядом с другими прогонами памяти не хватит.
2. **`obs.starting_stacks` на первом решении.** Есть везде, где раздачу ведёт наш движок: `HandState` записывает
   `starting_stacks` при раздаче (`engine.py:246`) и кладёт их в каждое `Observation` (`engine.py:362`); это
   стеки до блайндов. Дуэли (`duel.py:230`, `duplicate.py:126`), матчи с мозгом и веб-стол идут через `play_hand`
   с явными стеками — годится. Slumbot-адаптер строит `HandState` сам, стеки там всегда 200bb — сетка выродится в
   одну точку, это нормально. Пустой список возможен только у чужих обёрток: fallback на `spec.stack_bb` уже есть
   в `CoreSearchAgent._starting_stacks` — повторить в обёртке.
3. **Логи рук для AIVAT.** Обёртка должна класть в `decision_info()` точку сетки и файл blueprint'а первого
   решения раздачи (`{"point": 50, "blueprint": "…hunl50w3_pot16_s0.bin"}`), `eval_archetypes` пишет это в
   `hero[0]`. Тогда `aivat_eval` нужен `--blueprints <манифест>` и выбор lookup'а по раздаче — расширение
   маленькое (модели известного игрока на blueprint, ~105 МБ каждая, строятся лениво). Но есть тонкость с
   **корнем**: таблица корня AIVAT считается для конкретных стартовых стеков (`--stack-bb`), при переносе стеков
   они меняются от раздачи к раздаче — либо считать корневой член на лету (256 розыгрышей на класс — дорого), либо
   принимать на дискретных точках: дубль-сдачи при стеках = точка сетки (для каждой точки уже есть корневой кэш
   родного blueprint'а), а дуэль с переносом стеков — только как есть (сырой счёт), для санитарной проверки.
   Предлагаю приёмку строить именно так: точки сетки с AIVAT + перенос стеков как есть.
4. **3-max.** `min(свой, max(живых оппонентов))` как основное правило — верно для решений, где важен самый глубокий
   соперник (все ставки против него), и совпадает с тем, как считают эффективный стек в hand-tracker'ах. Спорно
   при трёх разных стеках: если короткий оппонент — тот, с кем реально идёт розыгрыш, точка завышена. Дешёвая
   проверка внутри той же дуэли: логировать альтернативы (`min(свой, min(опп))` и медиану) и потом посчитать,
   как часто выбор различался бы; менять правило только по замеру. 3-max-сетки blueprint'ов пока нет — сначала
   HU.
5. **Что добавить.** (а) Обёртка — только по стартовым стекам раздачи (до блайндов), без гистерезиса — правильно,
   выбор на раздачу. (б) Для стеков выше сетки — верхняя точка (200bb), ниже нижней — нижняя (20bb); записать в
   манифест. (в) Внутренний `CoreSearchAgent` уже ищет на реальных стеках (`SubgameSearch(res.game,
   self._starting_stacks(obs), …)`), но диапазоны в корне и префлоп берёт из blueprint'а — поэтому blueprint
   точки должен быть один и тот же для агента поиска и для диапазонов (так и выходит при `SearchResources` на
   точку). (г) Правило «каждый шаг бьёт предыдущий»: сначала дуэль обёртки из чистых BlueprintAgent'ов против
   одиночного 200bb на точках 50/100/150 с AIVAT (ожидание по шагу 1: +18 на 50bb, +5 на 100bb, ≈ 0 на 150bb —
   прогноз запишу до замера, когда ставим в очередь); поиск внутри точек — следующим шагом. (д) Не делать
   интерполяцию между соседними blueprint'ами без замера: Pluribus этого не делал, а смесь двух средних стратегий
   может быть хуже любой из них.
Итог: против плана возражений нет; до постановки в очередь — правка `SearchResources.build` для общего бакетера
и `--blueprints` в `aivat_eval`, обе маленькие.

### 7.1 Прогноз до замера (записан до запуска дуэлей)

Условия для всех трёх точек: `--spec 2p_<d>bb_river`, широкая сетка 0.5,1,3 / 0.5,1,2,4, 3 рейза, таблицы корзин
`data/bucket_tables`, 25 000 дубль-сдач (50 000 рук), `--seed 0`, `--log-hands`; герой — сетка из чистых BlueprintAgent
по манифесту `data/stack_grid_pot16_s0.json`, соперник — одиночный `blueprint_hunl200w3_pot16_s0.bin`. AIVAT — первые
20 000 рук, известный игрок — герой, `--blueprints` манифест, 4 потока.

Логика: при стеках, равных точке сетки, сетка на каждой раздаче выбирает эту точку и играет бит в бит как одиночный
blueprint точки (проверка 7.2), так что дуэли на 50bb и 100bb — это дуэли шага 1 «родной против 200bb»
(`docs/stack_depth.md` §5) на 25 000 сдачах seed 0 вместо 1 000 000 сдач seed 1. Если blueprint'ы в `data/` — те же
файлы, что на ноуте, первые 20 000 рук здесь — те же сдачи и те же решения, что первые 20 000 из 50 000 рук AIVAT шага 1.

| глубина | точка | прогноз, как есть (25k сдач) | прогноз, AIVAT (20k рук) | основание |
|---|---|---|---|---|
| 50bb | 50 | +18 ± 8, выигрыш значим | +18 ± 6, выигрыш значим | шаг 1: +18.2 ± 1.3 (1M сдач); AIVAT первых 50k рук seed 0: +18.0 ± 3.7 |
| 100bb | 100 | +5 ± 11, ноль не исключён | +3 ± 6, ноль не исключён | шаг 1: +5.4 ± 1.8; AIVAT первых 50k рук seed 0: +2.7 ± 3.7 |
| 150bb | 150 | +1 ± 13, ноль не исключён | +1 ± 6, ноль не исключён | замера нет (гипотеза): потеря 200bb-blueprint'а на чужой глубине как степень log2 отношения глубин по двум замерам (4× → 18.2, 2× → 5.4, показатель 1.75) даёт на 150bb (1.33×) +1.2; линейно по log2 — +2.2, квадратично — +0.9 |

Ширина полос: как есть — ±1.3 и ±1.8 шага 1, пересчитанные с 1M на 25k сдач (×6.3); для 150bb — между 100bb и
±11.6 дуэлей 200bb на 25k сдачах (`data/duels64`); AIVAT — ±3.7 шага 1, пересчитанные с 50k на 20k рук (×1.6).
Ещё до замера: каждая рука с решением героя — на точке, равной стеку (ни одной на соседней); в памяти одна точка.

Санитарная проверка с переносом стеков (задача 5c). В коде оценки (`negpluribus/eval`) переноса стеков нет: и
`duplicate_match`, и `duplicate_duel` ставят каждой раздаче стеки из `--spec`. Перенос есть в библиотеке —
`CashTable(reset_stacks=False)` (`negpluribus/table.py`): стеки переносятся, разорившийся докупается до `stack_bb`,
у победителя фишки остаются (сумма растёт с каждой докупкой, в отличие от веб-столика, где при разорении оба садятся
заново), колоды случайные (не дубль-сдачи), агенты между раздачами не сбрасываются, лога рук нет. На нём — санитарный
прогон как есть, не приёмка: 100 000 рук, старт 100bb, seed 0, сетка против одиночного 200bb. **Прогноз:** руки на
точках от 20 до 200bb, больше всего на 50–100bb; сырой результат сетки положительный, около +8 ± 7 bb/100 (смесь
глубин ≤ 100bb, где сетка по шагу 1 выигрывает от +5 до +18).

Дополнение до замера (после прогона на `CashTable`, до этого прогона): второй санитарный прогон — с правилом

## 8. H4: перевод исчезнувших сайзингов в олл-ин (агент H4, 29.09)

**Дефект (H4, охотник за дефектами).** Blueprint, обученный глубже стола (одиночный 200bb на столе 50bb; точка
сетки выше стека стола — по замыслу раздела 3), хранит вероятность на сайзингах, фишки которых на этом столе
достают до стека. `BetGrid.abstract_actions` перечисляет вместо них олл-ин «a», а поиск по строке
(`BlueprintStrategy.policy`, C++ `BlueprintTable::policy_at`) перенормировал их массу на остальные легальные имена.
Пример: строка 200bb после «r1 r3» (SB открыл в банк, BB 3-бет 3× банка) с r3 = 80 % на 50bb, где легальны
f, c, r0.5, a, — вместо пуша колл/фолд в пропорции остальных действий; строка целиком на таких сайзингах — None,
то есть чек/колл «вне карты».

**Правило (реализовано, ветка `worktree-agent-a52674af316d7271b`).** Сайзинг строки, которого нет среди легальных
имён и который больше всех сайзингов, общих у легальных имён и строки, отдаёт свою вероятность олл-ину, если «a»
легален. Фишки растут с долей банка, поэтому это ровно сайзинги, упёршиеся в стек. Остальные отсутствующие имена —
как раньше (перенормировка): сайзинг ниже легального (сжатый на тот же мин-рейз), всё, когда олл-ин нелегален
(против олл-ина). Правило стоит в самой функции поиска по строке — Python `policy_of_row`
(`negpluribus/cfr/strategy.py`) и C++ `policy_at` (`csrc/persist.h`), одни и те же числа в одном порядке, — поэтому
за ним идут все: агенты, диапазоны / раскаты / строки оценщика поиска, модель агента в AIVAT. На родной глубине все
имена строки легальны — числа прежние бит в бит. Лимит рейзов убирает сайзинги, но не олл-ин (узел f / c / a), и
число рейзов записано в истории ключа, так что строки таких узлов сайзингов не имеют.

Вместе с H4 — **QA-1** (тестировщик): рейз не в олл-ин в узле, где достигнут лимит рейзов (действия узла только
f / c / a), переводился в «r1» / «r3», которых у узла нет, и все дальнейшие ключи руки были неизвестны. Теперь такой
рейз — «a» (Python и C++ `from_concrete`, исходы перевода AIVAT). В дуэлях blueprint'ов на одной сетке рейз в таком
узле всегда олл-ин, так что QA-1 в замерах ниже ничего не меняет (проверяется счётом по логам).
