## 1. Правила (действуют, переданы пользователем)
1. **Правило пользователя** (дословно, через сенсея): «оптимизаторка не должна строить главные узлы. Либо по очень чёткому ТЗ от вас. Она только оптимизировать должна».
   - Распределённое обучение тебе поручает сам пользователь. Но дизайн (п. 4) перед реализацией покажи ему и сенсею, получи «да».
2. **Не трогать** `core` и `master`/`main`. Работа — в своих ветках `opt/*`, пушить только в свои ветки. **PR — только если попросят.**
3. **Тип (а) / (б).**
   - (а) — та же математика: скорость, память, раскладка. Приёмка бит в бит (однопоточно) или в пределах шума (многопоточно).
   - (б) — другая математика: прунинг, float, отложенные обновления и т. п. Помечать явно, не реализовывать без одобрения, давать список с источниками и оценкой.
4. **Числа помечать:** [замер] / [источник] / [оценка] / [гипотеза]. Честно писать, что не сделано и где проверка слабая.
5. **Большие файлы данных не коммитить:** блюпринты, таблицы корзин (~138 МБ и больше), чекпоинты.
6. **Решения — только пользователь.** Мы предлагаем, с механизмом, замером и планом проверки.

## 2. Проект за минуту
NegativePluribus — покерный бот в стиле Pluribus: Python + C++-ядро через pybind11 (`csrc/`, модуль `negpluribus._fastcore`).

| файл | что |
|---|---|
| `csrc/engine.h`, `evaluator.h` | движок раздачи, оценка рук |
| `csrc/abstraction.h`, `handindex.h`, `buckettable.h` | корзины (E[HS], potential-aware), индекс рук Waugh, таблицы корзин (`NEGPLURIBUS_BUCKET_TABLES`) |
| `csrc/mccfr.h`, `histtree.h`, `nodetable.h` | CPU-тренер MCCFR (обычный и пакетный режим `batch_size`), дерево историй, таблица узлов, `TableGroup` (рост таблиц) |
| `csrc/flatgame.h`, `flatcfr.h` | **плоское дерево + уровневый пакетный тренер `FlatTrainer`** — основа распределёнки |
| `csrc/gpucfr.cu`, `gpukernels.h`, `cfrmath.h`, `philox.h` | GPU-ядра; общая арифметика CPU/GPU; Philox4x32-10 |
| `csrc/workers.h` (ветка `opt/trainer-oom`) | ошибки рабочих потоков → исключение Python вместо аварии |
| `csrc/search.h` | поиск в реальном времени (моя зона, не трогать) |
| `scripts/train_blueprint.py` | обучение (`--gpu 0 --batch 16384 --checkpoint-every N --resume`) |
| `scripts/build_fast.py` | сборка ядра |

**Главное о пакетном режиме** (он же GPU и он же база распределёнки):
- пакет выровнен по абсолютным итерациям; внутри пакета все читают таблицы на начало пакета, обновления применяются после;
- итерация t: раздача Philox(seed, t), баттон t % n, вес Linear CFR = t;
- сэмпл соперника — Philox, адресованный (seed, t, traverser, хэш истории), то есть **не зависит от порядка обхода**;
- обновления ячейки суммируются в порядке (итерация, обходчик) → каждая сумма — тот же double, что у эталона.

Из этого следует главное: **ветку можно считать где угодно, результат тот же до бита**, если соблюдён порядок применения.

**Качество пакетного режима** (проверка сенсея, `2026-09-27_batch-epsilon.md`):
- пакетная итерация ≈ 0.8 обычной (пачка 4096) / 0.75 (16384);
- пачку 65536 не использовать;
- нужно ≥ 1000 пачек за прогон.

## 4. Задача: распределённое обучение. Что уже есть
Читать: **`from-optimizer/2026-09-28_DISTRIBUTED_DESIGN.md`** (схема) и ветку **`opt/distributed`** (`77f1c33`):
- `FlatTrainer.partition_stats`;
- `scripts/partition_stats.py`;
- цифры в `docs/partition_stats_3max_wide.txt`.

**Замер** [замер, облако; 3-max 100bb, широкая сетка, 16 корзин, после 2M итераций]:

| граница | ветвей | доля работы «верха» | обмен на пакет 16384 |
|---|---|---|---|
| флоп | 1 077 | 6.9 % | ~1.1 МБ |
| тёрн | 15 787 | 21.7 % | ~2.4 МБ |

- Работа делится ровно до 4 машин. На 8 машинах самая загруженная берёт 17 % вместо 12.5 %.
- **Память неровная:** одна ветка флопа (вероятно, лимп втроём) держит 26.6 % всех ячеек.

**Выбранная схема «верх у всех, ветки у хозяев»** (бит в бит с пакетным `FlatTrainer`):
1. Верх (префлоп) целиком есть на каждом узле: таблица и вычисление.
   - Каждый узел сам генерирует раздачи пакета (Philox) и корзины (таблица корзин на каждом узле).
   - Прямой проход верха идёт везде, поэтому каждый знает, какие корни его ветвей достигнуты. Запросов по сети нет.
2. Ветка после флопа принадлежит одному узлу. Он считает её для всех заходов пакета и применяет свои записи у себя в порядке (итерация, обходчик).
3. Хозяин рассылает всем значения в корнях своих ветвей: 8 байт на заход, ~1 МБ на пакет.
4. Обратный проход верха все делают одинаково, из одних значений. Записи верха применяются локально, поэтому верх у всех совпадает бит в бит.
5. Цена — повтор верха на каждом узле (~7 %). Оценка ускорения без учёта сети: ×1.87 / ×2.64 / ×3.31 / ×5.39 на 2 / 3 / 4 / 8 узлах.
6. **Память:** крупные ветки флопа режутся по тёрну («смешанная граница»). Верх растёт до ~7–10 % работы, самая крупная часть — около 5 %.

**Отброшено** (с причинами в дизайне):
- верх вскладчину — теряется бит в бит, 4–12 МБ на машину;
- независимые прогоны с усреднением — для CFR некорректно;
- пересылка полных пакетов обновлений — десятки МБ.

**Идея пользователя «узел = исполнитель, а не компьютер»** — в схеме работает:
- CPU+RAM — один исполнитель, GPU того же компьютера — другой;
- ветки делятся пропорционально скорости и памяти;
- главная польза — память: 5070 (12 ГБ) + 32 ГБ RAM дают блюпринт в 2–3 раза больше, чем «только GPU»;
- 3050 — исполнитель для мелких ветвей;
- **внутри одного GPU резать дерево не нужно:** уровневый проход уже параллелит всё.

## 5. План реализации (предлагаемый, согласовать с пользователем)
1. **В одном процессе, потоки** — `FlatTrainer` с владением ветвями:
   - маска решений «чьё»;
   - проход верха для всех заданий, ветки — только свои;
   - обмен значениями корней через интерфейс (сначала — общая память);
   - **приёмка:** N «виртуальных узлов» в одном процессе = обычный пакетный `FlatTrainer` бит в бит: таблицы, `export_nodes()`, блюпринт. Как `[cpu]/[emu]/[gpu]` в `tests/test_flatcfr.py`.
2. **Несколько процессов на одной машине** (TCP localhost), затем LAN.
   - Координатор: список узлов, скорость, память → раздача ветвей жадно по работе с учётом памяти.
   - Приёмка та же, бит в бит.
3. **GPU как исполнитель ветвей:** ядра стартуют не с корня игры, а с корней своих ветвей (элементы уровня 0 — корни ветвей). Твоя 3050 — первый полигон.
4. Смешанная граница флоп/тёрн под память узлов.
5. **Чекпоинты:** каждый узел пишет свои ветки, координатор собирает общий файл в прежнем формате.
   - Продолжение с чекпоинта — бит в бит (как в `tests/test_trainer_oom.py`).
   - Отказ узла на середине пакета не должен портить таблицы остальных: пакет применяется у всех или ни у кого.
6. **Замеры:** провод против Wi-Fi, 2 процесса на ноуте, ноут + ПК, скорость и сколько ждёт сеть. Сначала на игре, которая влезает на один узел: есть эталон для сравнения.

**Быстрая проверка вместо «гонять 2 дня»:**
- бит в бит на малой игре — это минуты, не дни;
- длинные прогоны нужны только для скорости и масштаба, не для корректности.

3. Транспорт: чистый TCP-сокет в C++ или Python (`asyncio`/`socket`) поверх ядра? Совет: Python-координатор + C++-вычисления, обмен numpy-буферами.
   1 МБ на пакет — Python не узкое место.

## 7. Мудрость (что я выучила на своих ошибках)
**Проверки:**
- **Бит в бит — главный инструмент.** Однопоточный режим детерминирован: сравнивай hex всех float (как `search_bench --compare`). Многопоточный — статистически: `search_mt_check`, разброс сидов внутри одной сборки как контроль.
- **Python 3.12+ обязателен:** `py_sum` в C++ повторяет компенсированный `sum()` CPython 3.12. На 3.11 побитовые тесты падают.
- **Флаги сборки:** `-ffp-contract=off` / `/fp:precise`, в CUDA `--fmad=false`. Не включать FMA и `-ffast-math`: сломают совпадение.
- **Меняешь порядок сложения — это уже не бит в бит.** SIMD-суммы, другой порядок применения обновлений — тип (б) или «в пределах шума».
- **`tail` глотает код возврата.** Я один раз закоммитила с падающим тестом. Проверяй `pytest` без пайпа или с `set -o pipefail`.
- **Тесты, падающие случайно,** — это обычно многопоточная фикстура. Фикстуры обучай на 1 потоке.
- Каждый сценарий падения (OOM и т. п.) — в отдельном дочернем процессе теста, иначе авария убьёт pytest.

**Память и потоки:**
- Узлы таблиц не двигаются при росте (арены), слоты — двигаются. Любой рабочий поток должен регулярно заходить в `get_or_create` или явно `if (group->pending()) group->arrive()`, иначе рост таблицы ждёт вечно.
- Горячие счётчики и контексты потоков — на отдельных кэш-линиях (`alignas(64)`). Один общий атомарный счётчик на каждую итерацию — узкое место на многих потоках; брать пачками.
- P/E-ядра: работа раздаётся динамически, закреплять потоки не нужно. 12 или 14 потоков — мерить.
- Не запускать тяжёлое параллельно с замером скорости: числа поплывут. На ПК пользователя без подкачки не запускать одновременно обучение GPU и поиск: 32 ГБ на двоих мало.

**Прочее:**
- **Windows:** путь к таблицам — без кириллицы. Сборка — `python scripts/build_fast.py`.
- Не делай `pkill -f <шаблон>`, который совпадает с командной строкой твоего же шелла.
- **Отчёт:**
  - первым — итоговая таблица «было / стало»;
  - затем проверка качества;
  - затем что сделано по коммитам;
  - в конце — что НЕ сделано и почему.

  Пользователь читает начало.
