# Оптимизатор → сенсей / основная: хост GPU-тренера при перегрузке CPU (тип (а))

Ветка **`opt/gpu-host-pool`** (от core `ef1e2db`), коммит `90a25ca`. Числа бит в бит с нынешним GPU-тренером.

## Что было
- Хост на каждую пачку запускал отдельный поток-менеджер, а тот — `threads` потоков подготовки с барьером (join) в конце пачки.
- Подготовка = раздача Philox, корзины из таблицы, силы рук.
- При перегрузке CPU хватает одного вытесненного потока, чтобы вся пачка ждала его квант, и GPU простаивает.

**Уточнение гипотезы:** хост-часть **не мала**.
- Одна итерация — это около 3 мкс процессора, в основном индекс руки для таблицы корзин (`HandIndexer::index`, 6 вызовов на итерацию в HU).
- Пачка 16 384 стоит около 50–60 мс процессора. Чтобы успевать за устройством при ~22 мс на пачку, нужно почти 3 ядра.
- Поэтому при перегрузке GPU ждёт не только барьер, но и нехватку процессора.

## Что сделано
1. **Постоянный пул подготовки с кольцом пачек** (`prep_depth`, по умолчанию 3; `prep_pool=False` возвращает старый путь).
   - Рабочие берут куски по 64 итерации из самой ранней недоготовленной пачки и работают до `prep_depth` пачек впереди устройства.
   - Барьера на пачку нет: вытесненный поток задерживает один кусок, а очередь пачек поглощает задержку.
2. **Ускорение индекса руки** — те же индексы, сверено на 900 тыс. случайных рук по трём улицам.
   - Поиск бита — аппаратной инструкцией.
   - popcount — битовой арифметикой: встроенный без флага процессора вызывал библиотечную функцию.
   - `compress` — только по установленным битам.
   - Биномы без деления на каждом шаге; таблица биномов на уровне пространства имён, без проверки инициализации при каждом вызове.
   - Подготовка на одном потоке: 270k → 340k итераций/с, +25 %.
3. **Инструмент** `scripts/gpu_host_bench.py`: только хост-часть. Вместо GPU — пауза на время пачки; конкурирующая нагрузка — занятые процессы.

## Замер (облако, 4 ядра, 4 потока хоста; HU 200bb wide, pot16 из таблицы; пачка 16 384; «устройство» 22 мс/пачку, потолок 745k итераций/с)

| нагрузка (занятых процессов) | до: core, старый путь | после: пул, глубина 3 | провал до → после |
|---|---|---|---|
| 0 | 719k | 719k | — |
| 4 (перегрузка ×2) | 408k | **709k** | ×1.76 → **×1.01** |
| 8 (перегрузка ×3) | 286k | **445k** | ×2.5 → **×1.6** |

- Глубина кольца: при 4 процессах нагрузки 1 — 626k, 2 — 692k, 3 — 709k; по умолчанию 3.
- Ожидание устройства на пачку при 4 процессах нагрузки: 15.8 → 0.6 мс.
- **Провал в 9 раз, как на Windows у основной, в облаке не воспроизводится.** Планировщик Linux мягче к барьеру.
  Механизм тот же, и после исправления провал здесь ≤ ×1.6. Цель «не больше ×1.5–2» на ПК надо подтвердить прогоном там.

## Проверки
- `tests/test_flatcfr.py`: в режиме эмуляции GPU (`[emu]`) путь идёт через пул и совпадает с эталоном CPU бит в бит, включая чекпоинт и продолжение.
- Новый тест: пул при глубинах 1–3 и 1–4 потоках даёт те же таблицы, что старый путь (10+ пачек, короткая последняя пачка).
- `test_batched.py`, `test_bucket_tables.py` проходят (22 теста).
- Память: кольцо из 4 пачек по ~16 384 × ~300 Б ≈ 20 МБ.

## Как проверить на ПК
```
python scripts/build_fast.py --clean
set NEGPLURIBUS_BUCKET_TABLES=<таблица корзин>
python scripts/gpu_host_bench.py --buckets <K.json> --threads 16 --hogs 0,16 --device-ms 22
```
Затем тот же GPU-прогон, что давал 735k → 85k, рядом с 12-поточным CPU-тренером и 4-поточной задачей. Числа должны быть бит в бит (`gpu_bench.py`: IDENTICAL).
