Ветки (от core **`b03512a`**), в core не вливала, решение за пользователем:
- **`opt/search-speed2`** `4d60396` — MCCFR-поиск;
- **`opt/vector-speed`** `18506ab` — векторный режим.

Все числа — [замер] в облаке: 4 ядра Xeon 2.8 ГГц, разброс между прогонами ±5–10 %. Числа ПК даст только прогон основной (п. 6).

## Итог коротко
- **×2 без изменения результата не получилось.** Флоп +15–18 %, тёрн +27–28 %, ривер +13 %; векторный DCFR −15–17 % времени.
- Флоп — главное время руки при E8 — упирается в объём работы на итерацию: узлов на итерацию много, каждый недорог. Дальнейшие правки того же рода дали бы ещё единицы процентов.
- В память флоп не упирается: при 5.6M итераций таблица всего ~325k узлов (абстракция корзин), it/s как на малом масштабе. Поэтому предзагрузка узлов не нужна.
- **Путь к ×2 на флопе — только тип (б)**, прежде всего прунинг по регретам (Pluribus MCCFR-P). По решению пользователя сейчас делаю его как опцию с замерами: `opt/search-pruning`, отдельный отчёт.

## 3. Что сделано
1. **Индекс рук:** перенос из `opt/gpu-host-pool` — ctz/popcount битовой арифметикой, C(n,k) без деления; индексы те же.
2. **`regret_matching`:** компенсированная сумма CPython только по положительным регретам. Нули не меняют ни сумму, ни компенсацию, поэтому тот же double; вызов вдвое дешевле.
3. **Корзины ривера пакетом из таблицы** (`TabulatedBucketer::river_buckets_all`). Раньше в корнях флопа и тёрна каждая раздача × место считала индекс руки заново — 14 % времени тёрна.
   - Цена: построение таблицы ривера на доску — тёрн ~10 мс; флоп ~0.2 с на 1 потоке / ~60 мс на 4, на ПК ~20 мс. Кэшируется на доску.
4. **Поиск:**
   - на 1 потоке без блокировок узлов;
   - у соперника одна критическая секция вместо двух;
   - терминалы и листья отвечаются инлайном, кадр функции — только для узлов решения;
   - контексты потоков на своих кэш-линиях;
   - номера итераций пачками по 16;
   - наш узел ищется один раз на поток (проверка роста таблицы осталась раз в итерацию).
5. **Вектор:**
   - в терминалах вскрытия чистятся только руки на доске (win/tie не чистятся вовсе);
   - строки σ собираются одним проходом по рукам;
   - множители DCFR берутся из таблицы (`pow` был 5 %);
   - обнуление v совмещено с первым накоплением (0.0 + x, те же знаки нулей).

## 4. Обзор техник (кратко; подробности — в черновике раунда)
| техника / источник | вывод |
|---|---|
| Lock-free MCTS (Enzenberger & Müller 2009), Hogwild! (Recht et al. 2011) | узлы без блокировок: +15 % на 4 потоках (диагностика), но это тип (б) — редкие потерянные обновления |
| Параллельный MCTS, virtual loss (Chaslot et al. 2008); lc0/KataGo — пакеты NN | в MCCFR ветка сэмплируется, virtual loss не нужен; NN в поиске нет |
| Ложное разделение, пачечная раздача работы | сделано |
| SIMD / SoA регрет-матчинг | SIMD меняет порядок сложения → не бит в бит; для (а) — только срез нулей |
| Counter-based RNG (Philox) | xoshiro дешёв (<1 %), не нужно |

**P/E-ядра:** итерации раздаются динамически (счётчик пачками по 16), статического деления нет. Медленные E-ядра просто берут меньше итераций, закреплять потоки не нужно. 12 или 14 потоков — мерить на ПК.

## 5. Тип (б): что даст больше (не реализовано в этих ветках)
1. **Прунинг по регретам в поиске** (Pluribus MCCFR-P, в Pluribus — для блюпринта).
   Предварительно, 1 тёрн-корень, 100k итераций, 1 поток: узлов на итерацию в 3 раза меньше, время ×2.6 меньше, но ε на итерацию хуже (9.3 → 13.7).
   Решает сравнение при **равном времени** — в работе, `opt/search-pruning`, отчёт отдельно.
2. **Узлы без блокировок:** +15 % на 4 потоках [замер, диагностика].
3. **Отложенные обновления горячих узлов у корня:** оценка +10–30 % на 14 потоках.
4. **float вместо double для регретов:** память ×0.5, оценка +10–20 % на больших флоп-таблицах.
