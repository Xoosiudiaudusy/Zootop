# Оптимизатор: распределённое обучение блюпринта — дизайн-план (отложено ради vector CFR)

Ветка `opt/distributed` (от core `ef1e2db`), коммит `77f1c33`: анализ `FlatTrainer.partition_stats` +
`scripts/partition_stats.py`. Сырые цифры — `docs/partition_stats_3max_wide.txt` в ветке.
Статус: **замер сделан, схема выбрана, реализация не начата.** По решению пользователя сначала vector CFR для поиска.

## 1. Замер [замер, облако]

3-max, 100bb, широкая сетка, 16 корзин (ячейки ×4 при 64), стратегия после 2M итераций пакетного тренера. 32 768 итераций анализа.

| граница | веток | работа «верха» | переходов на итерацию | значений на пакет 16384 | сырые записи верха на пакет | суммированные записи верха, на машину |
|---|---|---|---|---|---|---|
| флоп | 1 077 | **6.9 %** | 8.3 | **1.1 МБ** | 42 МБ | 4.3 МБ |
| тёрн | 15 787 | 21.7 % | 18.3 | 2.4 МБ | 120 МБ | 11.6 МБ |

- При равномерной стратегии (итерация 0) доля верха выше: 26 % на флопе. Обученные стратегии чаще сбрасывают на префлопе.
- Работа между машинами делится ровно: до 4 машин — идеально, на 8 машинах самая загруженная берёт 17 % вместо 12.5 %.
- **Память — неровно.** Одна ветка флопа (вероятно, лимп втроём) держит 26.6 % всех ячеек. По тёрну самая крупная ветка — 5.5 %.

## 2. Выбранная схема: «верх у всех, ветки у хозяев» (бит в бит с пакетным режимом)

- **Верх** (префлоп) есть на каждом узле целиком: таблица и вычисление.
  - Каждый узел сам получает раздачи пакета (Philox по номеру итерации) и корзины (таблица корзин на каждом узле).
  - Прямой проход верха идёт на каждом узле для всех итераций, поэтому каждый узел сам знает, какие корни его веток достигнуты.
    **Запросов по сети нет.**
- **Ветка** после флопа принадлежит одному узлу.
  - Он считает её для всех переходов пакета и применяет свои записи у себя в порядке (итерация, обходчик), как эталон.
  - Затем рассылает всем значения в корнях своих веток: 8 байт на переход, около 1 МБ на пакет суммарно.
- **Обратный проход верха** идёт на каждом узле одинаково, из одних и тех же значений.
  Записи верха применяются локально, и верх у всех совпадает бит в бит. Обновления верха по сети не ходят.
- **Цена** — повтор работы верха на каждом узле (6.9 %). Ускорение без учёта сети: ×1.87 / ×2.64 / ×3.31 / ×5.39 на 2 / 3 / 4 / 8 узлах.
- **Сеть**: около 1 МБ на пакет. По гигабиту около 0.01 с при пакете в 0.25 с (CPU, 16 потоков). Wi-Fi тоже потянет, но провод предпочтительнее.
- **Проверка** — совпадение бит в бит с `FlatTrainer` в пакетном режиме (как `[cpu]`/`[emu]`/`[gpu]` в `test_flatcfr.py`).
  Сначала — несколько процессов на одной машине.

### Память: смешанная граница
Ветки флопа крупнее порога режутся дальше по тёрну: их флоповая часть становится частью верха, тёрновые подветки раздаются хозяевам.
Это немного увеличит повторяемый верх (оценка: 7–10 % работы) и сделает самую крупную часть около 5 %. Порог выбирается под память узлов.

### Отброшено
- **Верх вскладчину** (каждый узел считает верх только для своих итераций): 4–12 МБ на машину на пакет, и совпадение бит в бит теряется.
- **Независимые прогоны с усреднением**: для стратегий CFR это некорректно.
- **Пакеты по сети**: обмен полными обновлениями, десятки МБ на пакет.

## 3. Узел — это исполнитель, а не компьютер (идея пользователя)

Идея пользователя: «CPU + RAM — один узел, GPU на том же компьютере — другой». **В этой схеме так и работает.**
Узел — это любой исполнитель, который держит свои ветки и умеет их считать:
- **GPU** (своя видеопамять) — ядра уже есть. Их нужно научить стартовать не с корня игры, а с корней своих веток.
  Уровневый проход это позволяет: элементы уровня 0 — корни веток.
- **CPU + RAM** — уровневая CPU-версия `FlatTrainer`.
- Внутри одного компьютера «сеть» — это память или PCIe. Обмен в 1 МБ на пакет ничего не стоит.

Что это даёт:
1. **Скорость.** Ветки делятся пропорционально скорости исполнителя.
   GPU 5070 в 7–10 раз быстрее 16 потоков CPU, поэтому CPU того же ПК возьмёт около 10 % веток. Это +10 %, скромно.
2. **Память — главное.** Ветки, не влезающие в видеопамять, лежат в RAM.
   5070 (12 ГБ) + 32 ГБ RAM — это вдвое-втрое больший блюпринт, чем «только GPU». 3050 (4 ГБ) на ноуте тоже полезна как узел для мелких веток.
3. Смешанный кластер: ПК (GPU + CPU) + ноут (GPU + CPU) = 4 исполнителя в одной схеме.

**Внутри одного GPU разрезать дерево по веткам не нужно.** Пакетный уровневый проход уже параллелит всё
(итерации × обходчики × узлы уровня), и это бит в бит с эталоном. Деление на ветки нужно, только когда исполнителей несколько.

## 4. План реализации (когда вернёмся)
1. `FlatTrainer`: владение ветками (маска решений), проход верха для всех заданий и веток только для своих; обмен значениями через интерфейс.
   Сначала — потоки в одном процессе, проверка бит в бит.
2. Процессы на одной машине через сокеты (TCP, localhost), затем LAN. Координатор: список узлов, скорости, память → раздача веток (жадно по работе, с учётом памяти).
3. GPU как исполнитель веток (ядра с корнями веток вместо корня игры).
4. Смешанная граница флоп/тёрн для памяти.
5. Чекпоинты: каждый узел пишет свои ветки, координатор собирает общий файл (формат прежний).
