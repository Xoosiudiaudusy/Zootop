# GPU-тренер MCCFR: проект и статус (оптимизатор, 26.09)

Одобрено пользователем: «да давай пробуй делай… По шагам. Начинай с 1». Ветка `opt/gpu` (от `opt/next`).
В облаке нет GPU. CUDA-часть можно написать и собрать под `sm_120`/`sm_89`, но мерить и проверять — только на ПК пользователя (RTX 5070) или ноутбуке (4060).

## Идея
Прямой перенос (одна раздача на поток) плох: 32 потока warp'а расходятся по веткам дерева и случайным адресам.
Вместо этого **пачка раздач и обход по уровням дерева истории**:
1. B раздач генерируются на GPU генератором Philox4x32-10 (адрес случайного числа = seed, итерация, назначение, индекс);
   корзины — индекс Waugh + таблица корзин в VRAM; силы рук на вскрытии.
2. Прямой проход по уровням: элемент = (раздача, узел истории). Обходчик — все действия, соперник — одно сэмплированное.
   Элементы уровня **сортируются по узлу**: warp работает с одним узлом, одинаковое число действий, строки сожалений из кэша.
3. Обратный проход: значения детей → значение узла, прибавки к сожалениям.
4. Применение: сортировка обновлений по ключу + сегментная сумма (CUB) в фиксированном порядке. Результат детерминирован и равен CPU-эталону **бит в бит**.
   Альтернатива побыстрее — свёртка в warp + atomicAdd, но порядок плавает.
5. Вся последовательность ядер одного шага — CUDA Graph.
Данные: вся таблица сожалений в VRAM (HU-16 ~0.4 ГБ, HU-256 ~3 ГБ), double (узкое место — память, не FP64).
Оценка: ×10–30 к CPU ПК [оценка, не замер].

## Шаг 1 (сделан): CPU-эталон пакетного алгоритма — коммит bd02139
`Trainer::batch_size` (`set_batch`, `train_blueprint --batch B`): итерации пачки читают стратегию на начало пачки, обновления
применяются после неё в порядке (ключ узла, вид, действие, итерация, номер). Пачки выровнены на абсолютные номера итераций,
поэтому чекпоинты надо ставить кратно B. Раздачи и сэмплы — Philox (Random123 known answers в тестах).
Результат одинаковый при любом числе потоков (тест). Это эталон, с которым GPU должен совпасть бит в бит. `batch = 0` — обычный тренер, без изменений.
Тип (б) при B > 1: пачка видит одну стратегию.

**Качество, пуш/фолд 10bb** (точная эксплуатируемость bb/100, среднее 3 сидов; 30k / 100k / 300k / 1M итераций) [замер]:
| B | 30k | 100k | 300k | 1M |
|---|---|---|---|---|
| обычный | 9.68 | 3.76 | 1.61 | 0.57 |
| 1 | 8.64 | 3.17 | 1.24 | 0.47 |
| 64 | 8.79 | 3.22 | 1.27 | 0.48 |
| 1024 | 8.77 | 3.10 | 1.24 | 0.47 |
| 16384 | 25.96 | 4.83 | 1.41 | 0.49 |
До 1024 не хуже обычного. 16384 медленнее на старте (мало обновлений стратегии), к 1M догоняет. Игра крошечная, в большой игре инфосет редко встречается дважды в пачке [гипотеза].
**HU 100bb, 4 улицы, узкая сетка, E[HS]-8, 20M итераций, seed 0, дуэль 200k раздач против обычного тренера** [замер]:
| B | разница, bb/100 (±≈1.9; шум сидов обычного тренера −1.0) | время (1 поток CPU-эталона) |
|---|---|---|
| 4096 | **+0.3** — не хуже | 3445 с |
| 65536 | **−11.3** — заметно хуже (всего ~305 обновлений стратегии за 20M) | 4235 с |
Вывод: пачка ~4 тыс. раздач безопасна, 65 тыс. на этой длине прогона нет. Для GPU этого хватает:
4096 раздач × 2 обходчика × ~160 узлов ≈ 1.3M посещений узлов на пачку, до ~100k элементов на уровень при ~73k потоков 5070 [оценка].
CPU-эталон медленный (запись и сортировка каждого обновления, ×5 к обычному в 1 поток), на CPU им не пользоваться. Он нужен только для проверки GPU.

## Шаги дальше
2. Плоский формат для GPU: дерево истории (CSR: действия, дети, терминалы с вкладами), плотная раскладка сожалений `[узел][корзина][действие]`, таблица корзин, индекс Waugh.
3. CUDA: ядра раздачи и корзин, прямой и обратный проход по уровням, сортировка и сумма обновлений, CUDA Graph; сборка под sm_120 и sm_89.
4. Проверка на ПК: GPU = CPU-эталон бит в бит на малой игре; скорость в узлах/с против CPU; Nsight Compute.
