# Можно ли снизить обмен на пачку (вопрос пользователя, 29.09 13:10)

Игра: 3-max 100bb wide, pot16, старт с 100M, пачка 16384. Узлы: GPU 3050 + GPU 4060. Замеры:
`results/2026-09-29_two_laptops.txt`, `bench/exchange_bytes.py`.

## 1. Из чего складываются 1.16 МБ и 2.32 МБ [замер]

- **Переходы.** За пачку 152–154 тыс. переходов, 3.14 на job (job = итерация × ходящий игрок).
- **Что едет.** Сейчас верх считает каждый узел, поэтому список переходов (какая итерация в какой корень ветки
  заходит) каждый узел выводит сам. Сдача детерминирована по (seed, t), верх у всех один — списки занимают **0 байт**.
  Едут только значения: 8 байт (double) на переход, от владельца ветки каждому узлу с верхом.
- **2 GPU.** Каждое значение пересекает провод один раз. 65.6 тыс. переходов в ветки 3050 и 79.8 тыс. в ветки 4060
  дают 145 тыс. × 8 Б = **1.16 МБ** (по счётчикам координатора). Служебного — заголовки кадров, меньше 1 кБ, около 0.1 %.
- **4 узла.** Добавляется ещё 1.16 МБ, это чистая потеря топологии. CPU-узел 4060 получает все значения через Wi-Fi,
  в том числе 638 кБ, которые родились на том же 4060 и съездили к координатору на 3050 и обратно.

## 2. Нижняя граница по механике

- **Верх везде.** Каждое значение перехода должно один раз попасть на другую машину: 8 Б × 154 тыс. = 1.23 МБ
  (сырой double). Списки — 0 Б. Бит в бит требует точный double: float32 или фиксированная точка — это тип (б).
- **Верх на одном узле** (вариант 1). У узла веток нет верха, поэтому нужен список (корень, job): 8 Б сырых. Обратно
  едет значение, 8 Б. И то и другое — только для переходов в чужие ветки (65.6 тыс., ветки 3050). Сырые 1.05 МБ,
  со сжатием ~0.25 МБ [оценка по замеренным степеням сжатия, п. 3].
- **4 узла.** Если значения машины пересекают провод один раз, а по узлам той же машины раздаются локально, получается
  столько же, сколько у 2 GPU: 1.16 МБ.

## 3. Сжатие [замер: настоящий проход, 1.23 МБ значений, одно ядро ноутбука]

**Значения** сильно повторяются: различных 20.9 %, самое частое встречается 8 175 раз, нулей 5.3 %. Поэтому хорошо
работают словарные компрессоры:

| способ | степень | сжатие + распаковка |
|---|---|---|
| zstd 1 | 2.28× | 4.8 + 3.2 мс |
| zstd 3 | 2.51× | 5.5 + 2.2 мс |
| zstd 10 | 2.70× | 37.6 мс на сжатие |
| lzma | 3.24× | медленно |
| перестановка байтов по плоскостям | 2.03× | хуже без неё: повторы идут целыми double |

**Списки (корень, job)** сжимаются в 8.7× (lzma), до 0.92 Б на переход. Дельты job и номера корней как varint дают
2.5 Б на переход, со сжатием — 0.84 Б.

## 4. Обвязка без сети [замер: 3050, 1M итераций, один GPU-узел]

- В одном процессе — 352 715 ит/с (46.4 мс на пачку); через TCP по localhost — 324 007 (49.8 мс), то есть **−8 %**.
- Из этих 3.4 мс: передача 1.2 мс, копии и контрольные суммы на стороне узла ~1.9 мс, digest верха каждую пачку
  0.4 мс, координатор ~0.
- Что убирается:
  - не слать значения, когда узел один;
  - `memoryview` вместо `bytes` — без копий;
  - digest верха реже;
  - узлы одной машины — в одном процессе (как `DistTrainer`) или через общую память.
- На 4060 разрыв выглядел как 28 % (403k против 292k), но то был короткий прогон (262k) с прогревом, а localhost на 4060
  медленный: ECHO 130–280 МБ/с против 1.6 ГБ/с на 3050. [гипотеза] Loopback на 4060 фильтрует VPN или сетевая защита.
  Проверка — тот же замер при выключенном VPN.

## 5. Конвейер: что прячется, а что нет [источник: зависимости алгоритма]

- **Внутри пачки:** обмен прохода p идёт, пока считается проход p+1. Это уже сделано.
- **Последний проход пачки прятать не за чем.** Прямой проход пачки k+1 начинается с верха и берёт его σ после сложения
  пачки k. Обратный проход верха пачки k требует все значения. Это барьер снимка стратегии; перекрытие пачек меняет
  числа, то есть тип (б).
- **Законные перекрытия (тип (а)):**
  - (а) сложить обновления своих веток — ~95 % обновлений, верх ≈ 5.4 % работы — пока едут значения последнего прохода,
    и только потом обновления верха. Ячейки верха и веток не пересекаются, порядок в ячейке прежний. Прячет до ~8–10 мс
    пачки;
  - (б) последний проход сделать маленьким: открытая часть обмена пропорциональна его размеру, а размер прохода
    чисел не меняет;
  - (в) подготовка итераций следующей пачки — уже делается.
- **Критический путь пачки** ≈ счёт всех проходов + обмен последнего прохода + обратный проход верха последнего
  прохода + сложение верха.
- **Жёсткий предел** — пропускная способность провода: ит/с ≤ полоса / байт на пачку, как ни перекрывай.
  По Wi-Fi (7.5 МБ/с) это 1.16 МБ → 155 мс на пачку, то есть не больше ~106k ит/с. Замерено 80–82k.

## Итог: 2 GPU (3050 + 4060), пачка 16384

| шаг | байт на пачку | Wi-Fi 7.5 МБ/с | гигабит ~110 МБ/с |
|---|---|---|---|
| сейчас (сырые double, верх везде) | 1.16 МБ | **82k ит/с** [замер] | ~360–440k [оценка] |
| + zstd 3 на значения (2.5×, ~8 мс процессора) | 0.46 МБ | ~230–260k [оценка]: сеть ~62 мс против 155 | без выигрыша: 11 мс сырыми против ~4 + 8 мс |
| + вариант 1 и сжатие (списки 0.9 Б + значения ~3 Б, только чужие переходы) | ~0.25 МБ | ~300k+, упор в счёт [оценка] | ~410–470k [оценка] |
| + сложение веток во время последнего обмена | — | мало | +2–5 % [оценка] |
| + обвязка (без копий, digest реже) | — | +1–2 % | +3–5 % [оценка] |
| 4 узла: обмен через ретранслятор на каждой машине | 2.32 → 1.16 МБ | 36–42k → ~80k сырыми, ~230k со zstd [оценка] | ~300k, упор в CPU-узлы [оценка] |

Для сравнения: одна 4060 — 292k (TCP) / 403k (в процессе); одна 3050 — 324k (TCP, 1M) / 353k.

**Ответ «никак не снизить?»** Снизить можно:
- **По Wi-Fi главный рычаг — сжатие значений:** ×2.5 меньше байт при ~8 мс процессора на пачку. Затем вариант 1:
  по проводу едут только переходы в чужие ветки, а списки сжимаются в 9 раз.
- **По гигабиту** обмен и так прячется за счётом. Там решает вариант 1, потому что верх считается один раз, и
  законные перекрытия. Сжатие по гигабиту не нужно.
- Всё это тип (а), числа не меняются.
